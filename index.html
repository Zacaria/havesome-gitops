01 / LE MODÈLE

Décrire ce qui doit être.
Observer ce qui est.

Vous connaissez terraform plan : une configuration exprime une intention, l'outil la compare à des ressources existantes. GitOps reprend cette idée de déclaration, mais ajoute un agent qui observe et réconcilie continuellement.

Le raccourci utile
Git est le lieu de l'intention approuvée. Le cluster est la réalité. Le contrôleur travaille à réduire l'écart.
01

Déclaratif

Décrire le résultat souhaité plutôt que la suite de commandes pour l'obtenir.

02

Versionné

Conserver l'intention et son historique immuable, avec ses auteurs et sa revue.

03

Tiré automatiquement

Un agent autorisé récupère l'état désiré depuis la source.

04

Réconcilié en continu

Il observe le réel et agit pour le rapprocher de l'intention.

Ces quatre principes viennent d'OpenGitOps. Une CI qui lance simplement kubectl apply n'assure pas à elle seule cette boucle.

Le Deployment indique 2 réplicas dans spec.replicas.

↻   Écart de configuration détecté : selon ses réglages, le contrôleur GitOps peut rétablir spec.replicas à 3. Kubernetes tente ensuite de maintenir les pods. Une ressource appliquée n'est pas forcément une application saine.

Dérive

Une modification manuelle, un autre contrôleur ou une panne peut créer un écart. Selon la configuration et les champs gérés, la réconciliation peut corriger la dérive ; elle peut aussi échouer ou ignorer certains champs.

Responsabilités

Le contrôleur GitOps applique l'intention ; les contrôleurs Kubernetes font converger leurs ressources. Une image introuvable ou un manque de capacité peut empêcher les pods de devenir prêts.

04 / LE DÉPÔT

Rendre l'intention
lisible.

Une organisation possible sépare la base réutilisable des différences d'environnement. Ce n'est pas une structure obligatoire : choisissez des frontières de revue, de droits et de déploiement adaptées à l'équipe.

Une source, des responsabilités
Évitez que deux contrôleurs ou Terraform et GitOps gèrent simultanément les mêmes champs.

EXEMPLE / DEPLOYMENT KUBERNETES
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalogue
spec:
  replicas: 3
  selector:
    matchLabels: { app: catalogue }
  template:
    metadata:
      labels: { app: catalogue }
    spec:
      containers:
        - name: catalogue
          image: nginx:1.27

Extrait minimal pédagogique, sans politique de sécurité ni contrôles de santé : ne pas appliquer tel quel en production. En pratique, référencez l'image par digest et adaptez les ressources, probes et droits.

05 / LIVRER

Une promotion est
une décision traçable.

1

Construire

La CI teste le code, construit une image et publie un artefact identifiable, idéalement par digest.

2

Proposer

Une pull request met à jour la référence dans la configuration de staging. Validation, revue et contrôles précèdent la fusion.

3

Promouvoir

Après vérification en staging, une autre PR propose le même digest pour la production. Les règles d'approbation restent propres à chaque environnement.

4

Revenir

En cas d'incident, un revert ou une nouvelle PR rétablit une version connue. Vérifiez compatibilité des données et migrations : un retour d'image n'annule pas une migration de schéma.

La CI produit et vérifie ; le contrôleur GitOps récupère et applique. Une commande manuelle d'urgence peut être nécessaire : documentez-la, puis réconciliez l'intention pour ne pas voir le correctif annulé.

06 / SÉCURISER

Git n'est pas
un coffre-fort.

Secrets : séparer référence et valeur

Ne commitez jamais un secret en clair. Utilisez un gestionnaire de secrets ou des fichiers chiffrés avec une gestion de clés contrôlée. Les droits de déchiffrement, la rotation et la révocation font partie du système.

Un Secret Kubernetes encodé en base64 n'est pas chiffré par ce seul encodage. Protégez aussi l'accès API et le stockage du cluster.

Terraform n'est pas GitOps

Terraform peut créer réseau, cluster et contrôleurs ; GitOps peut ensuite gérer les charges dans le cluster. La frontière exacte dépend de l'équipe. Le state Terraform est distinct de Git : il peut contenir des secrets et doit être protégé, avec verrouillage adapté.

sensitive masque l'affichage mais n'empêche pas, à lui seul, le stockage dans le state.

Avant la production · Protéger les branches, limiter les droits du contrôleur, vérifier les artefacts, auditer les accès et tester la restauration. Une revue Git ne remplace pas une politique d'accès.

07 / CHOISIR

Des outils différents.
La même boucle.

Comparer les capacités et l'exploitation, pas seulement les captures d'écran.

Argo CD

Contrôleur GitOps Kubernetes avec interface web et modèle Application. Synchronisation automatique et auto-correction se configurent explicitement.

Documentation Argo CD ↗

Flux

Ensemble de contrôleurs Kubernetes composables ; ses ressources Source, Kustomization et HelmRelease décrivent la livraison et la réconciliation.

Concepts Flux ↗

Kustomize / Helm

Outils de composition ou de packaging des manifests, pas des contrôleurs GitOps à eux seuls. Argo CD et Flux peuvent les utiliser.

Kustomize ↗ · Helm ↗

Le rollback intégré d'Argo CD n'est pas disponible lorsque l'auto-sync est activée ; revenir à une intention connue dans Git reste un chemin traçable. Les options exactes dépendent de la version et de la configuration.

PREMIERS RÉFLEXES

Observer l'écart

  • Lire la révision attendue et celle observée.
  • Vérifier la synchronisation, les événements et l'état des pods.
  • Repérer le premier message d'erreur utile.

PRATIQUE EXPÉRIMENTÉE

Réduire le rayon d'impact

  • Définir droits, propriétaire de champs et dépendances.
  • Mesurer délai de convergence, échecs et santé réelle.
  • Répéter promotion, restauration et réponse à incident.
SYMPTÔME → PROCHAINE VÉRIFICATION

Git est à jour, pas le cluster ? Vérifiez l'accès à la source et la révision observée. Synchronisé, mais service indisponible ? Inspectez readiness, événements, image, ressources et dépendances. « Synced » n'est pas synonyme de service fonctionnel.
